- **Parser**: function arguments, the SELECT list, GROUP BY and ORDER BY are now collected on parser-owned scratch stacks and copied once into exact-size slices (previously grown with `append` from a fixed capacity). A `FunctionCall` with up to three arguments shares one allocation with its argument array, and a `SelectStatement` shares one with its single `From` entry and, for up to four columns, its `Columns` array. Parse allocations drop 28% on `aggregate` (18 to 13) and 12% on `complex` (50 to 44), and allocs/op fall on every SELECT shape. Layout-randomized amd64 CI gate runs on identical parser code disagree on time significance: run 41744051257 (Xeon 6973P-C) measured the parse geomean at -1.02% (p=0.289, not significant) and `aggregate` at -3.18%; run 41747404356 (Xeon 8573C) measured geomean -1.29% (p<0.001) and `aggregate` -2.45% (p<0.001), with A/A' flagging 0 of 52 benchmarks in both. No gated benchmark regressed in either run, allocs/op fall on every SELECT, ParseRW, ParseFresh, Normalize, Transform and ParseError row, and the gate on the merge with current main is quoted in the PR description. User-visible: `Columns`, `GroupBy`, `OrderBy` and `FunctionCall.Arguments` now have `len == cap` (they used to carry spare capacity), so a caller that appends to them reallocates instead of writing into spare space; trees are otherwise identical (guarded by the behaviour goldens). Lifetime trade-off: because the blocks are co-allocated, retaining only `Columns`, `From` or `Arguments` of a released tree keeps the whole block (up to 600 B) alive. No exported API change. [W4-04]
